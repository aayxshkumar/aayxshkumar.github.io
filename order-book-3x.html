From 21M to 68M ops/s: two changes to a C++ order book

29 October 2026

I'm building lob-engine, a limit order book in C++20, to learn how matching engines are made fast. This is a log of the first two optimisations, with the numbers at each step, the step that made things slower, the benchmark that turned out to be too kind, and a replay of 20 minutes of real exchange data.

The mixed workload is 1M operations from a seeded generator: 55% limit orders within 50 ticks of the mid price (a tenth of them crossing), 40% cancels and 5% market orders. It peaks at about 109,000 resting orders. Every version is in the repo and lob_bench runs them side by side.

v0: the baseline, and how I know it's right

An order book keeps resting buy and sell orders sorted by price, and orders at the same price in arrival order. An incoming order that crosses the spread trades against the best opposite price first, oldest order first.

v0 is the textbook version. Each side is a std::map from price to a level. Orders come from a pre-allocated pool, and each level chains its orders in an intrusive doubly linked list, so resting an order never allocates and a cancel is O(1) once the order is found. Finding it is a std::unordered_map from order id to pool slot.

Before optimising anything I wanted a way to tell whether a faster version was still correct. The test suite includes a deliberately naive reference book (plain vectors, linear scans), and a differential test pushes 20,000 random operations through both, comparing every trade and the whole book after every step.

My first version of that test passed with a bug planted in it. The random orders crossed the spread so often that queues never formed, so time-priority bugs had nothing to break. Biasing the flow towards passive orders and adding explicit "increase size at the same price" modifies fixed it. Since then I plant bugs by hand to check the tests catch them; it's 16 so far, and the tests catch all of them. You can step through five of them on the home page.

v1: flat arrays, which made it slower first

Exchanges limit how far prices can move, so the price levels can live in a flat array indexed by tick: finding a level becomes one subtraction instead of a tree walk. I gave each side an array covering 65,536 ticks and cached the index of the best level.

The cost moves to the moment the best level empties, when the next one has to be found. I added a benchmark for the case that should hurt: 50 asks spaced far apart, cleared one at a time by market orders.

1,000-tick gaps2.0 µs14.8 µs1.85 µs

The array was slower than the map, but the first row didn't make sense: with 1-tick gaps there's almost nothing to scan, yet it was the slowest. The cost didn't depend on the gap at all. When the last ask was cleared, the scan walked the whole 65,536-tick band looking for an ask that didn't exist. The book already counted its levels, so it now checks the count and skips the scan when a side is empty.

That left real gaps. The fix is one bit per price level, set while the level has orders. Finding the next non-empty level then checks 64 levels per step with std::countr_zero, which beats following std::map pointers even with 1,000 empty ticks between levels.

v2: the benchmark was flattering std::unordered_map

After v1, the largest cost left was looking orders up by id. Every add checks for a duplicate, every cancel looks the order up, and every fill removes one. std::unordered_map allocates a node per order, and each lookup follows a bucket pointer and then a node pointer.

Before replacing it I looked at what the benchmark fed it. The generator numbered orders 1, 2, 3 and so on. That's unusually kind to unordered_map: with libc++, consecutive ids land in consecutive buckets, and nodes allocated one after another tend to sit close together in memory. Real venues send ids that look random. Scrambling the same ids with a bijective mixer (the splitmix64 finaliser, so they stay unique) cost v1 a quarter of its throughput, from 34.4M to 25.7M ops/s.

The replacement, IdTable, is about 100 lines:

  • A flat array of 16-byte entries, each an order id and a pool slot.
  • Linear probing, kept at most half full, so a lookup usually touches one or two neighbouring entries.
  • Fibonacci hashing: multiply the id by 264/φ and keep the top bits. One multiply, and sequential ids still spread out.
  • Backward-shift deletion instead of tombstones. When an entry is removed, later entries in the same run move back to fill the hole, so a book that runs all day doesn't fill up with dead entries.
  • A fixed capacity, taken from the order pool, so it never rehashes.

Backward shift is easy to get subtly wrong when a run wraps past the end of the array, so the table has its own differential test against std::unordered_map: 20 seeds of 20,000 inserts and erases in a 16-slot table, where nearly every run is long and many wrap. I planted four bugs in the deletion code and it caught all four. A fifth survived, and it took me a minute to see why: it swapped two checks in a way that can't change the result. That's an equivalent mutant, not a gap in the tests.

The first benchmark result was confusing. With random ids, v2 was 40% faster. With sequential ids it was no faster at all. The benchmark sized the book for one million orders, so the table had 221 entries, 32 MB, far bigger than the cache, and every lookup was a cache miss. The workload never has more than 109,000 live orders. Sized for 256,000, the table is 8 MB, and v2 is roughly twice as fast as v1 with either kind of id.

So the honest version of the result comes with a condition: a fixed table's memory follows the capacity you configure, not the orders you have. Size it for the peak you expect, not the biggest number you can think of.

On real data

A seeded generator is easy to fool yourself with, as the ids showed. So I recorded 20 minutes of Binance's public BTCUSDT feed (11,992 depth updates and 71,328 trades) with a small recorder that uses only Python's standard library. It follows Binance's procedure for keeping a local book and stops at the first sequence gap.

Binance publishes price levels, not individual orders, so the replay has to invent orders that explain each change. A level that grows gets a new order for the difference. A level that shrinks loses size from its newest orders. A trade becomes an incoming order at the trade price, which fills the oldest orders there. After every update, the replay checks the book's top 10 levels on each side against the exchange's.

The first version of that check found a bug in my translation. A single update can clear an ask and place a bid at the same price. Applying the bid first crosses the stale ask and invents a trade that never happened, so each update now applies its reductions before its additions.

Throughput, 562,850 order operations15.9M ops/s81.9M ops/s

That's 5.2×, more than on the synthetic workload, though I wouldn't read much into the difference: at most 4,203 orders were resting at once, so the whole book fits in cache. The mix was 54% adds, 40% cancels and 6% size reductions, close to what the generator produces.

The top of book matched the exchange after 99.93% of updates. The other 0.07% come from the feed, not the book. Binance doesn't sequence trades against depth updates, so a trade sometimes arrives after the update that already includes it, and the replay removes that size twice until the next update for the level corrects it. Replaying the same recording without trades matches after every update.

What I can't measure yet

These are throughput numbers. Latency percentiles are harder on this machine: on Apple Silicon steady_clock ticks every 41.7 ns, so the fastest operations measure as zero or one tick. My latency tool measures the clock first and warns when it's too coarse, and it reports tick counts rather than pretending to have nanoseconds. Next I'm running on Linux with a TSC-based timer and perf stat, to get real percentiles and cache-miss counts for each version.

The code, the benchmarks and the recorder are at github.com/aayxshkumar/lob-engine. If you see something I've measured wrong, I'd like to hear about it: aayushkumr25@gmail.com.
