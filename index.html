lob-engine

A limit order book with price-time priority. Orders come from a pre-allocated pool, and each price level keeps its orders in an intrusive list, so adding an order never allocates and cancelling one is O(1).

v1 replaced the std::map price levels with two flat arrays indexed by price tick, plus a bitset of which levels are non-empty. On a mixed workload of 1M operations (Apple M4, clang 17, -O3, median of 3 runs) it went from 20.1M to 34.0M operations per second.

Benchmarkv0 std::mapv1 array + bitset
Mixed workload, 1M ops20.1M ops/s34.0M ops/s
Add + cancel, warm book32.5 ns28.5 ns
Sparse book, 1,000-tick gaps2.0 µs1.85 µs

The first array version was slower on sparse books. It found the next price level by walking empty ticks one at a time, and when a side emptied completely it walked the whole 65,536-tick band. The bitset finds the next level 64 ticks at a time; the full-band walk was a bug, and the level count now catches it.

Testing

Every operation is checked against a deliberately naive reference book over 20,000 random steps, and both the old and new books run the same 22 tests. My first version of that test passed with a bug planted in it: the random flow crossed the spread so often that queues never formed, so priority bugs had nowhere to show up. Once I biased the flow towards passive orders and added same-price size increases, it caught every bug I planted by hand, 12 so far across the matching rules, the array book and the bitset.

You can try five of them below. It's a JavaScript port of the matching rules replaying a short hand-written scenario; the C++ and the 20,000-step test are on GitHub.

    Log

    2026-10 · A benchmark found a full-band scan in my "faster" version

    I added a sparse-book benchmark because flat arrays should lose when price levels are far apart. They did, but not for the reason I expected: the cost didn't change with the gap. Clearing the last ask made the book scan all 65,536 ticks looking for an ask that didn't exist. That cost 22.5 µs a sweep against 2.0 µs for std::map. Checking the level count fixed that, and a bitset fixed the real gaps.

    2026-10 · Apple Silicon's steady_clock ticks every 41.7 ns

    My p50 came out at exactly 42 ns, which is one tick of a 24 MHz clock. Anything faster than a tick shows up as one tick (or zero). The latency tool now measures the clock's resolution first and warns when it's too coarse. I use the M4 for throughput and Linux for percentiles.

    2026-10 · My first differential test passed with a planted bug in it

    The random flow crossed the spread so often that queues never formed, so priority bugs had nowhere to show up. Once I biased it towards passive orders and added explicit "grow at the same price" modifies, it caught all five bugs I had planted.
