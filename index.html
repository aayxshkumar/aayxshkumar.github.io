lob-engine

A limit order book with price-time priority. Orders come from a pre-allocated pool, and each price level keeps its orders in an intrusive list, so adding an order never allocates and cancelling one is O(1).

v1 replaced the std::map price levels with two flat arrays indexed by price tick, plus a bitset of which levels are non-empty. v2 replaced std::unordered_map for the id lookup with a flat open-addressing table. On a mixed workload of 1M operations (Apple M4, clang 17, -O3, median of 3 runs):

Benchmarkv0 std::mapv1 arrays + bitsetv2 + id table
Mixed workload, 1M ops21.2M ops/s34.3M ops/s67.5M ops/s
Same, random-looking ids20.0M ops/s30.4M ops/s60.1M ops/s
Add + cancel, warm book32.6 ns28.5 ns8.6 ns

Both steps had a catch. The first array version was slower on sparse books, because of a bug that walked the whole 65,536-tick band. And the benchmark numbered orders 1, 2, 3, which flattered std::unordered_map; with random-looking ids it lost a quarter of its speed. The write-up has both stories.

On 20 minutes of real Binance BTCUSDT data, replayed as 562,850 order operations, v2 is 5.2× faster than v0, and its top 10 price levels match the exchange's after 99.93% of updates. The recorder uses only Python's standard library, and a strict version of the replay runs in CI.

Testing

Every operation is checked against a deliberately naive reference book over 20,000 random steps, and the old and new books run the same 22 tests. My first version of that test passed with a bug planted in it: the random flow crossed the spread so often that queues never formed, so priority bugs had nowhere to show up. Once I biased the flow towards passive orders and added same-price size increases, it caught every bug I planted by hand, 16 so far across the matching rules, the array book, the bitset and the id table.

You can try five of them below. It's a JavaScript port of the matching rules replaying a short hand-written scenario; the C++ and the 20,000-step test are on GitHub.

    2026-10-29 · From 21M to 68M ops/s: two changes to a C++ order book

    The full story of v1 and v2, with the numbers at each step. The id table ran no faster with sequential ids until I noticed the benchmark had sized it at 32 MB for a workload that never holds more than 109,000 orders.

    2026-10 · A benchmark found a full-band scan in my "faster" version

    I added a sparse-book benchmark because flat arrays should lose when price levels are far apart. They did, but not for the reason I expected: the cost didn't change with the gap. Clearing the last ask made the book scan all 65,536 ticks looking for an ask that didn't exist. That cost 22.5 µs a sweep against 2.0 µs for std::map. Checking the level count fixed that, and a bitset fixed the real gaps.

    2026-10 · Apple Silicon's steady_clock ticks every 41.7 ns

    My p50 came out at exactly 42 ns, which is one tick of a 24 MHz clock. Anything faster than a tick shows up as one tick (or zero). The latency tool now measures the clock's resolution first and warns when it's too coarse. I use the M4 for throughput and Linux for percentiles.
